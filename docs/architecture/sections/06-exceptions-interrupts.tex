\section{Exception and Interrupt Model}

VIV-32 uses a single exception and interrupt entry mechanism. Synchronous exceptions,
software traps, system calls, and hardware interrupts all transfer control through the
exception vector mechanism.

\begin{itemize}
\item The current processor status is saved to \code{\%esr}.
\item The continuation address is saved to \code{\%epc}.
\item The exception cause code is written to \code{\%ecause}.
\item Exception-specific data is written to \code{\%edata}.
\item The interrupt-enable bit in \code{\%sr} is cleared.
\item Control transfers to a vector address derived from \code{\%evbase} and
      \code{\%ecause}.
\end{itemize}

\noindent
VIV-32 v\version\ defines machine mode only. User mode, supervisor mode, privilege
transitions, nested privilege stacks, and memory protection are reserved for future
versions.

\section{Exception Causes}

The \code{\%ecause} control register records the cause of the most recent exception or interrupt.

\begin{center}
\begin{tabular}{lll}
\hline
\code{ecause} value & Cause & Description \\
\hline
\code{0x00} & \code{RESET} & Reset entry \\
\code{0x01} & \code{IllegalInstruction} & Undefined, reserved or otherwise invalid instruction \\
\code{0x02} & \code{MisalignedFetchException} & Instruction fetch or control transfer to a non-word-aligned address \\
\code{0x03} & \code{MisalignedAccessException} & Misaligned halfword, word, or double-half load/store \\
\code{0x04} & \code{SoftwareTrap} &
      Software-generated exception raised by the \code{trap} instruction; the encoded
      \code{imm12} value is written to \code{\%edata}. \\
\code{0x05} & \code{SystemCall} & \code{syscall} instruction \\
\code{0x06} & \code{Interrupt} & Bus-attached device interrupt \\
\code{0x07} & \code{BusError} &  \\
\code{0x08--0xFF} & Reserved & Reserved for future architectural or platform causes \\
\hline
\end{tabular}
\end{center}

\noindent
Cause values above \code{0xFF} are reserved in VIV-32 v\version. Future versions
may define additional architectural, platform, or implementation-specific exception causes.

\section{Exception Vector Calculation}

The \code{\%evbase} control register contains the base address of the exception
vector table. Each exception cause has a 16-byte vector slot.

\begin{center}
\code{vector\_address \assign~\%evbase + (\%ecause <{}< 4)}
\end{center}

\noindent
The \code{\%evbase} register must contain a 16-byte-aligned address.

An attempt to write a value to \code{\%evbase} whose low four bits are non-zero is an
unrecoverable architectural error. The attempted value is not written to \code{\%evbase},
and the processor enters the halted state.
No exception is raised, because exception entry requires a valid exception-vector base address.
Execution remains halted until reset or platform-defined external action.

\begin{itemize}
\item Each vector slot is 16 bytes.
\item Each vector slot can contain up to four 32-bit instructions.
\item A vector slot may contain a short handler directly.
\item A vector slot may contain a jump to a longer handler elsewhere.
\end{itemize}

\section{Exception Entry Sequence}

When an exception or interrupt is taken, the processor performs the following architectural
actions:

\begin{enumerate}
\item Determine the exception cause.
\item Save the current processor status register to \code{\%esr}.
\item Clear the interrupt-enable bit in \code{\%sr}.
\item Save the current continuation address to \code{\%epc}.
\item Write the exception cause code to \code{\%ecause}.
\item Write exception-specific data to \code{\%edata}.
\item Set the program counter to
\code{\%evbase + (\%ecause <{}< 4)}.
\end{enumerate}

The value saved in \code{\%esr} is the complete pre-exception value of
\code{\%sr}, including the interrupt-enable bit and condition flags.

\noindent
Clearing the interrupt-enable bit prevents maskable interrupts from
interrupting the initial exception handler sequence. Software may
re-enable interrupts explicitly after saving any required state.

\section{Exception Program Counter}

The \code{\%epc} control register contains the continuation address saved when an exception
or interrupt is taken.

The continuation address is the address at which execution will resume if the handler returns
using \code{iret} without modifying \code{\%epc}.

For exceptions raised during execution of an instruction, the continuation address is normally
the address of the following sequential instruction:

$$
\code{\%epc} \leftarrow \code{\%pc + 4}
$$

This includes software traps, system calls, illegal instructions, misaligned data accesses,
and other exceptions detected while executing an instruction.

For an interrupt taken between instructions, \code{\%epc} receives the address of the next
instruction that would otherwise have executed.

For an exception raised while fetching an instruction, \code{\%epc} receives the address from
which instruction fetch was attempted. Returning without modifying \code{\%epc} therefore
retries the failed fetch.

Exception-specific addresses or other diagnostic information are recorded separately in
\code{\%edata}.

An exception handler may modify \code{\%epc} before executing \code{iret} in order to retry,
skip, or redirect execution.

\section{Exception Data Register}

The \code{\%edata} control register records data associated with the most recent
exception or interrupt.
The interpretation of \code{\%edata} depends on the exception cause.

\begin{center}
\begin{tabular}{lll}
\hline
\textbf{Event type} & \textbf{\code{\%edata} value} & \textbf{Meaning} \\
\hline
IllegalInstruction & Instruction address & Address of the invalid instruction \\
MisalignedFetchException & Instruction address & Misaligned fetch address or control-transfer target \\
MisalignedAccessException & Effective address & Address of the misaligned memory access \\
SoftwareTrap & Trap immediate & Encoded software-trap data \\
SystemCall & \code{0} & No architecture-defined exception data \\
Interrupt & Platform interrupt data & Interrupt-source information supplied by the platform \\
BusError & Transaction address & Address associated with the failed bus transaction \\
\hline
\end{tabular}
\end{center}

\noindent
The interpretation of platform interrupt data is defined by the platform specification.

\section{Status Register Interrupt State}

The \code{\%sr} control register contains the architectural condition flags
and interrupt-control state.
On exception or interrupt entry, the current value of \code{\%sr} is copied to
\code{\%esr} before \code{\%sr.IE} is cleared.
\code{\%esr} therefore contains the complete processor status that existed immediately
before exception entry, including all condition flags and the previous interrupt-enable state.
The active \code{\%sr} may then be modified by the exception handler without destroying
the saved pre-exception status.

\begin{center}
\begin{tabular}{lll}
\hline
Bit & Name & Meaning \\
\hline
\code{0} & \code{N} & Negative flag \\
\code{1} & \code{Z} & Zero flag \\
\code{2} & \code{C} & Carry flag \\
\code{3} & \code{V} & Overflow flag \\
\code{4} & \code{I} & Infinity flag \\
\code{5} & \code{U} & Underflow flag \\
\code{6} & \code{X} & Inexact flag \\
\code{7} & \code{E} & Arithmetic error flag \\
\code{8} & \code{IE} & Interrupt enable bit \\
\code{9--31} & reserved & Reserved, must be zero in VIV-32 v\version{} \\
\hline
\end{tabular}
\end{center}

The \code{\%esr} register uses the same bit layout as \code{\%sr}.
Bits 0--8 of \code{\%esr} correspond directly to the defined \code{\%sr} fields. Bits 9--31
are reserved and read as zero. Writes to reserved \code{\%esr} bits are ignored.
Consequently, restoring \code{\%sr} from \code{\%esr} using \code{iret} cannot introduce
non-zero values into reserved \code{\%sr} bits.

\noindent
When \code{IE} is set, maskable interrupts may be taken. When \code{IE}
is clear, maskable interrupts are held pending or ignored according to
platform interrupt-controller behaviour.

\begin{itemize}
\item The \code{ei} instruction sets \code{\%sr.IE}.
\item The \code{di} instruction clears \code{\%sr.IE}.
\item Exception and interrupt entry clears \code{\%sr.IE}.
\item The \code{iret} instruction restores \code{\%pc} from \code{\%epc} and restores
      \code{\%sr} from \code{\%esr}.
\end{itemize}

\section{Interrupts}

Hardware interrupts use the common exception-entry mechanism.

For an interrupt:

\begin{itemize}
\item \code{\%ecause} is set to \code{0x06}.
\item \code{\%edata} receives platform-defined interrupt-source information.
\end{itemize}

The exact interrupt sources, priorities, pending-bit behaviour, acknowledgement mechanism,
and interpretation of \code{\%edata} are defined by the platform specification.

\section{Software Trap}

The \code{trap} instruction raises a \code{SoftwareTrap} exception.

For a software trap:

\begin{itemize}
\item \code{\%ecause} is set to \code{0x04}.
\item \code{\%edata} receives the zero-extended 12-bit immediate operand encoded by the
\code{trap} instruction.
\end{itemize}

The interpretation of the trap data is defined by the execution environment.

\section{System Call}

The \code{syscall} instruction raises a \code{SystemCall} exception.

For a system call:

\begin{itemize}
\item \code{\%ecause} is set to \code{0x05}.
\item \code{\%edata} is set to zero.
\end{itemize}

The system-call number and arguments are passed according to the VIV-32 ABI.
The system-call ABI and execution-environment semantics are specified separately.

\section{Illegal Instruction}

An \code{IllegalInstructionException} is raised when the processor encounters an undefined
or reserved instruction encoding, or executes an instruction whose encoded
operation is architecturally invalid.

For an illegal instruction:

\begin{itemize}
\item \code{\%ecause} is set to \code{0x01}.
\item \code{\%edata} receives the address of the invalid instruction.
\end{itemize}

\section{Misaligned Access Exceptions}

A \code{MisalignedFetchException} is raised when the processor would transfer instruction
execution to an address that is not word-aligned.

This may occur either:

\begin{itemize}
\item while attempting to fetch an instruction from a misaligned address; or
\item while executing a control-transfer instruction whose calculated or register-supplied
target address is not word-aligned.
\end{itemize}

For a \code{MisalignedFetchException}:

\begin{itemize}
\item \code{\%ecause} is set to \code{0x02}.
\item \code{\%edata} receives the misaligned instruction address.
\end{itemize}

The value saved in \code{\%epc} follows the normal continuation-address rules:

\begin{itemize}
\item for an exception detected while executing a control-transfer instruction,
\code{\%epc} receives the address of the following sequential instruction;
\item for an exception detected while fetching an instruction,
\code{\%epc} receives the attempted fetch address.
\end{itemize}

A \code{MisalignedAccessException} is raised when a halfword, word, or double-half
load or store uses an effective address that does not satisfy its required alignment.

For a misaligned data access:

\begin{itemize}
\item \code{\%ecause} is set to \code{0x03}.
\item \code{\%edata} receives the effective address of the misaligned access.
\end{itemize}

Byte loads and stores never raise \code{MisalignedAccessException}.

\section{Bus Error}

A \code{BusError} exception is raised when an instruction fetch, load, or store cannot
be completed because the addressed bus transaction is unavailable or unsupported.

For a bus error:

\begin{itemize}
\item \code{\%ecause} is set to \code{0x07}.
\item \code{\%edata} receives the address associated with the failed bus transaction.
\end{itemize}

\section{Exception Return}

Exception and interrupt handlers return using the \code{iret} instruction.

On execution of \code{iret}:

\begin{itemize}
\item \code{\%pc} is restored from \code{\%epc}.
\item \code{\%sr} is restored from \code{\%esr}.
\end{itemize}

Restoring \code{\%sr} restores the complete pre-exception processor status, including
the condition flags and interrupt-enable state.

Consequently, \code{iret} does not unconditionally enable interrupts. If interrupts were
enabled before the exception was taken, they are enabled again on return; if they were
disabled, they remain disabled.

\section{Nested Exceptions and Interrupts}

Exception and interrupt entry clears \code{\%sr.IE}, preventing maskable interrupts from being
taken while the initial handler sequence executes.

Software may explicitly re-enable interrupts from within a handler, permitting nested or
reentrant interrupt handling.

The exception-state control registers are not stacked automatically. A subsequent exception or
interrupt overwrites:

\begin{itemize}
\item \code{\%epc};
\item \code{\%esr};
\item \code{\%ecause};
\item \code{\%edata}.
\end{itemize}

Software that permits nested exceptions or interrupts must preserve any exception state required
by the interrupted handler before re-enabling interrupts.

The storage location, ordering, nesting depth, and reentrancy mechanisms used for this
preservation are software policy and are outside the scope of the base architecture.
